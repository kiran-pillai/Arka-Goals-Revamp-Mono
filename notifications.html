Interactive wireframe: the avatar toggles the inbox; the right-side check marks read without navigating; selecting a notification opens and focuses the example check-in below. Sample notifications are not production data.

Behavior

  • Show the unread count on the avatar's top-right corner. Hide zero; cap the visible label at 99+ while preserving the exact accessible count.
  • Always render an avatar, including email-based initials when names are absent. Keep Sign Out separate.
  • Show read and unread items, newest first. Use cursor pagination with Load more so the entire history is reachable.
  • Opening the dropdown does not mark anything read. Selecting a notification marks it read after its check-in is located; explicit check actions mark it immediately.

States and accessibility

  • Loading: skeleton rows. Empty: "No notifications yet." Failure: "Could not load notifications" and Retry.
  • Unread rows use a tint and a text label, not color alone. Read actions have tooltips and accessible names.
  • Use Mantine Popover, Indicator, ScrollArea and ActionIcon with existing Tabler icons in the implementation. Escape and outside click close; restore focus to the avatar.
  • Constrain width to the viewport and height to available space. Failed read mutations restore the count and expose Retry.

02 / Find the check-in before scrolling

  1. Navigate to /?checkInId=<uuid>&notificationId=<uuid>. Add validated optional search fields to the home route in front-end/src/router.tsx. Never construct a selector from unchecked input.
  2. CheckInsPage.tsx loads the current member's check-ins. Notifications belong only to the check-in owner, so "My check-ins" includes the target. The current list is not paginated; if pagination is introduced, fetch the target explicitly instead of searching only the loaded page.
  3. Pass the target ID into CheckInTimeline.tsx, which owns the collapsed/expanded state. Add the ID to its expanded set and assign id="checkin-{id}" to the outer check-in element. Do not modify the unused table implementation.
  4. After data succeeds and the expanded DOM commits, call scrollIntoView({ block: 'start', behavior: 'smooth' }), use scroll-margin-top: 76px for the 60px header, and focus the target with tabIndex=-1 and preventScroll. Respect reduced motion and briefly highlight the destination.
  5. Only then mark the notification read. Prevent refetches from replaying the scroll; remove consumed search parameters with history replacement. A new selection, including the same target, must initiate a fresh scroll.
  6. If the target is deleted or inaccessible, show "This check-in is no longer available" and let the member explicitly dismiss the notification. Loading failures retain the target and offer Retry; do not use arbitrary timeouts.

03 / One durable notification per comment

Today CommentsService.addComment writes only a Comment. Add a Notification in the same database transaction so a failed write cannot leave half of the operation committed.

FieldType / rulePurpose
idUUID primary keyStable read-mutation and pagination identity
recipientIdUser FK, cascade deleteCheck-in owner, derived server-side
commentIdUnique Comment FK, cascade deleteExactly one notification per comment; actor and check-in available through Comment
createdAtDateTime, default nowNewest-first ordering
readAtNullable DateTimeNull means unread; server-set timestamp
model Notification {
  id          String    @id @default(uuid())
  recipientId String
  recipient   User      @relation(fields: [recipientId], references: [id], onDelete: Cascade)
  commentId   String    @unique
  comment     Comment   @relation(fields: [commentId], references: [id], onDelete: Cascade)
  createdAt   DateTime  @default(now())
  readAt      DateTime?

  @@index([recipientId, createdAt, id])
  @@index([recipientId, readAt])
}

// Add to User:    notifications Notification[]
// Add to Comment: notification  Notification?

No redundant actor or check-in ID is stored: join notification.comment.user for the name and notification.comment.checkIn for its date and target. Existing cascades remove notifications when their comment, check-in, or author is deleted. The API returns only the fields the inbox needs.

Write and authorization rules

  • In a transaction, load the target check-in, create the comment, and create its notification unless author = owner. The recipient is never accepted from the request body.
  • Foreign keys and the unique comment constraint enforce ownership links and prevent duplicate notifications for the same comment.
  • Every list, count, and read query scopes to the authenticated recipient. A member cannot read or mark another member's notification.
  • Read-one is idempotent: update only where readAt = null, preserving the original timestamp. Read-all uses a server-issued inbox snapshot cutoff so newly arriving comments remain unread.

API and freshness

  • GET /notifications?cursor=...&limit=20: items, next cursor, global unread count, server snapshot time. Stable ordering by createdAt then id.
  • PATCH /notifications/:id/read: authenticated, idempotent read acknowledgement.
  • PATCH /notifications/read-all: mark through the validated server snapshot; register the static route before the parameter route.
  • Cache per user; clear on logout. Poll every 30 seconds while visible, and refetch on focus, dropdown open, and successful read mutations. This is in-app delivery, not email or push.

04 / Delivery and acceptance

  1. Add the table and inverse relations using an additive migration. Existing comments are not backfilled; the inbox starts empty. Deploy the backend before the UI. Rollback can hide the UI and retain the unused table.
  2. Add transactional notification creation, recipient-scoped API endpoints, and tests for self-comments, other recipients, idempotent reads, cascade deletion, transaction failure and snapshot-bounded read-all.
  3. Add the avatar inbox and query hooks. Verify zero/99+ counts, empty/loading/error states, multiple pages, explicit read without navigation, failure rollback, focus restoration and nameless users.
  4. Add validated deep links and timeline expansion. Test cross-route and same-route navigation, delayed fetches, already-expanded targets, deleted targets, repeated clicks, mobile header offsets, and reduced motion.
Recommended defaults: no self-notifications, no historical backfill, mark on successful arrival, and 30-second visible-tab polling. These are design recommendations, not shipped behavior.

Design source: the existing Arka AppShell palette, 60px header, avatar treatment, Mantine layout conventions, and check-in timeline. This document deliberately matches the product instead of introducing a new design system.
