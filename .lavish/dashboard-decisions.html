What actually gets built

Three new tables, all user-scoped and cascading on user delete, matching CheckIn. No column added, renamed, or dropped on anything that already exists — so the migration needs no backfill and no dedupe.

The quarterly cadence — two clocks, not one

Your note that goals and give-ups are set at the start of each quarter and scoped to it gives the whole feature a second rhythm. The weekly check-in loop is unchanged; the quarter now brackets it.

This answers the question that was blocking implementation. Goals and give-ups are created in a one-time quarterly wizard, not inline on the dashboard and not during the weekly check-in. Three consequences worth naming: the dashboard needs an empty state for a user who hasn’t run setup yet, both Goal and Abstinence carry a quarter identifier so a new quarter starts clean, and because users can’t revise mid-quarter, there must be an admin editing surface — see below.
New surface: admin goal editing. Locking users out mid-quarter means an admin needs a real UI, not just an API route. This extends the existing /admin area (next to Manage invites): member list → that member’s goals for the quarter → inline edit of title and target date, plus an unlock toggle that hands revision back to the user. Gated on user?.role === 'ADMIN', the same check Manage invites already uses. It’s also the one place in the app where acting on someone else’s row is intended, so the role check needs a test of its own.

Completion semantics — your correction, and what it deleted

You clarified that “Pending” means the end date hasn’t arrived yet, not that someone still has to review it. That single change removed the reviewer role, the reviewedBy field, and any approval step.

Give-ups · SELF-RESOLVING

No user action needed

  • FAILED the moment brokenAt is set.
  • COMPLETED if the target date passes with brokenAt still null.
  • PENDING while the clock is still running.
  • Outcome is derived, not stored — targetDays plus brokenAt is enough.
Goals · USER CONFIRMS

Only you know if you made it

  • Nothing in the system can observe “ran a half marathon.”
  • outcome stays PENDING while now < targetDate.
  • The dashboard prompts you before the date arrives so you can claim it in time.
  • Past the date and still PENDING counts as FAILED — silence after the deadline isn’t ambiguity.
  • Resolved on your own say-so, so still no reviewer.
Data-integrity finding, from the live DB: 4 of the 5 existing check-ins belong to one user in week 2026-W33. Nothing currently stops a double-click from doing that again, so the backend phase adds a service-layer “already submitted this week?” guard in CheckInsService.create.

Why each cut was made

Four of these five came from you pushing back on the earlier draft. Recording the reasoning so it doesn’t get re-proposed later.

GoalPeriod enum
Was MONTHLY | QUARTERLY. Since goals are designed by quarter, the monthly variant has no meaning — every goal is quarterly, so the discriminator is dead weight. Goal now carries a quarter identifier instead of a period enum.
Season
You asked what it was actually tracking — and the answer was nothing that needed a table. Its three jobs each live better elsewhere: quarters are already implied by Goal.targetDate, the cadence is one hardcoded constant, and the submission-rate denominator is just “weeks since the user’s first check-in.”
Points & rank
Not relevant anymore. Removed the PointsLedger model, the scoring rule, and the “Rank #4 / 11” and “Points Available: 5” lines from the header. Kept in the plan’s appendix only as history of the original sketch.
CheckIn.weekKey
I argued for it on concurrency grounds and that argument was wrong — there is one person per account, so there are no concurrent submits to race. It’s derivable from createdAt, and a service-layer guard covers the double-submit case the DB constraint would have caught.
reviewedBy
Fell out of the completion-semantics correction. If “Pending” just means the date hasn’t arrived, there is no reviewer to record.
One thing the cuts can’t express: late submissions counting for the previous week. Deriving the week from createdAt pins a check-in to when it was written. If that ever needs to change, weekKey is the thing to revisit.
